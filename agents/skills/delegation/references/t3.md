# T3 Code Transport

The [delegation](../SKILL.md) operations for T3 Code threads, through the `t3 thread` CLI on the
host that runs the T3 server. Checked against T3 Code 0.1.10.

## Prerequisites

- T3 is available when `t3 thread list` succeeds in the repository: the server runs and the
    repository is a T3 project. Otherwise report that; do not start the server or add the project,
    since other `t3` subcommands ask.
- Run each `t3 thread` command as its own Bash call, with nothing chained, piped, redirected, or
    substituted around it. Only a whole call that is one `t3 thread` command leaves the sandbox;
    inside it, `t3` fails with `EPERM` on `~/.t3/userdata`.
- Run `git fetch origin` in a separate call before Start.

## Recipients

- Start Claude with `--provider claudeAgent` and Codex with `--provider codex`, always with
    `--model <slug>`. `t3 thread show <thread>` prints an existing thread's `<provider>/<model>`,
    which shows the form of a slug.
- Antigravity is never a recipient: its terms forbid another agent driving it on a subscription
    ([google-antigravity/antigravity-cli#1493](https://github.com/google-antigravity/antigravity-cli/issues/1493)).
- Do not use T3's `delegate_task`, subagents, or Agent Rooms for a lane: they move the work's
    steps inside T3.

## Guard Contract

The command hooks hold `t3 thread` to this contract; a call outside it is denied or asks.

- `start` runs only with an explicit `--provider claudeAgent` or `--provider codex` and a
    `--model`. A `start` without `--provider`, whose project default may be Antigravity, or with
    any other provider instance id is denied. `--base-dir`, `T3CODE_HOME`, and unknown options ask.
- `send` runs only to a thread this session started, which the hooks learn from the `threadId`
    that a successful `start --json` prints. A `send` to any other thread, such as the user's or the
    parent's, asks.
- `show` and `list` run as reads. Every other `t3` subcommand stays in the sandbox and asks.

## Operations

Put flags before the positional arguments, as `t3 thread <action> --help` shows them.

- **Start**, in the foreground and without `--wait`:
    `t3 thread start --worktree <base> --branch <branch> --provider claudeAgent --model <slug> --title <lane-name> --json . "Read your brief at <scratchpad>/briefs/<lane-name>.md and carry it out."`
    `<base>` is the fetched base ref, such as `origin/main`; T3 creates the worktree under
    `~/.t3/worktrees`. `.` is the T3 project that contains the current directory. The output is JSON
    with `threadId` and `runId`; keep `threadId` as the recipient identity. Without `--json`, or with
    `--wait` when the run ends with exit 1 or 2, the hooks do not learn the thread, and every later
    `send` to it asks.
- **Wait**, in the background right after Start:
    `t3 thread send --wait <thread> "When your task is done, reply with your final report as your brief asks."`
    A `send` never interrupts: a busy thread takes the message as its next turn, so the wait returns
    after the brief's turn and this short one. `--wait` has no timeout. Its exit code tells the
    outcome:
    - `0`: the run completed; the output is the reply.
    - `1`: the run failed or stopped. Read the thread and report it to the user; do not restart it
        unasked.
    - `2`: the recipient waits for an answer to an approval or a question. The user answers it in the
        T3 view; the parent never answers it, through `send` or otherwise. Tell the user which lane
        waits, then Wait again with the same command, which returns after the answered run and the
        new short turn end.
- **Prompt**, such as continuing a lane after `LANE-BLOCKED`, in the background:
    `t3 thread send --wait <thread> "<literal message>"`, with the same exit codes as Wait.
- **Read**: `t3 thread show --messages <n> <thread>` prints the state, the branch and worktree,
    `Waiting for <n> answer(s).` while an answer is pending, and the latest `<n>` messages in full.
    Read the thread after every Wait or Prompt instead of trusting a truncated reply.
- **Close**: the CLI cannot stop or archive a thread. Leave the thread in place; the user archives
    it in the T3 view.
- **Clean up**: after the user merges, run `cleanup_worktrees.py` by its absolute path with the
    home directory expanded, as shown in the rendered `excludedCommands` entry; `--dry-run` previews.
    It removes a lane worktree under `~/.t3/worktrees` on the same conditions as a Herdr one: a merged
    pull request's head is the branch tip and the tree is clean. Do not remove T3 worktrees by hand.
