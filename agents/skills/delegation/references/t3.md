# T3 Code Transport

The [delegation](../SKILL.md) operations for T3 Code threads, through the `t3 thread` CLI on the
host that runs the T3 server. T3 Code is the default transport. Checked against T3 Code 0.1.10.

## Prerequisites

- T3 is available when `t3 thread list` succeeds as an ordinary sandboxed Bash call in the
    repository: the server runs, the repository is a T3 project, and the installed hooks let
    `t3 thread` leave the sandbox, which they do only together with the
    [Guard Contract](#guard-contract). A success with the sandbox disabled proves none of that.
    Otherwise start no lane: report the reason to the user, as
    [Branches and worktrees](../../development-cycle/references/branches.md) describes, and never
    switch to another transport on your own. Do not start the server or add the project, since
    other `t3` subcommands ask.
- An implementation lane also needs its worktree to be cleaned after the merge. Hand one to T3
    only when the installed `cleanup_worktrees.py`, at the path the rendered `excludedCommands`
    entry shows, covers `~/.t3/worktrees`: its lane-root constant names that root, which
    `grep -E '^LANE_WORKTREES = .*\.t3/worktrees' <that path>` finds while a comment or docstring
    cannot match. Until then, start no implementation lane and report the reason to the user. A plan
    review creates no worktree and needs only the first condition.
- Run each `t3 thread` command as its own Bash call, with nothing chained, piped, redirected, or
    substituted around it. Only a whole call that is one `t3 thread` command leaves the sandbox;
    inside it, `t3` fails with `EPERM` on `~/.t3/userdata`.
- Run `git fetch origin` in a separate call before Start.

## Recipients

- Start Claude with `--provider claudeAgent --model claude-sonnet-5-5` and Codex with
    `--provider codex --model gpt-6.1-sol`. Both slugs are in the built-in model manifest of
    T3 Code 0.1.10 (`apps/server/src/provider/model-manifest.json`, checked on 2026-11-21); the
    CLI has no command that lists models, so recheck that file when T3 or the models change. The
    0.1.10 CLI cannot set the effort, so a T3 lane runs at the model's default effort in T3.
- Antigravity is never a recipient: its terms forbid another agent driving it on a subscription
    ([google-antigravity/antigravity-cli#1493](https://github.com/google-antigravity/antigravity-cli/issues/1493)).
- Do not use T3's `delegate_task`, subagents, or Agent Rooms for a lane: they move the work's
    steps inside T3.

## Guard Contract

The command hooks hold `t3 thread` to this contract; a call outside it is denied or asks.

- `start` runs only with an explicit `--provider claudeAgent` or `--provider codex` and a
    `--model`. A `start` without `--provider`, whose project default may be Antigravity, or with
    any other provider instance id is denied. `--base-dir`, `T3CODE_HOME`, and unknown options ask.
- `send` runs only to a thread this session started, which the hooks learn from the `threadId`
    that a successful `start --json` prints. A `send` to any other thread, such as the user's or the
    parent's, asks.
- `show` and `list` run as reads. Every other `t3` subcommand stays in the sandbox and asks.

## Operations

Put flags before the positional arguments, as `t3 thread <action> --help` shows them.

- **Start** an implementation lane, in the foreground and without `--wait`:
    `t3 thread start --worktree <base> --branch <branch> --provider <provider> --model <slug> --title <lane-name> --json . "Read your brief at <scratchpad>/briefs/<lane-name>.md and carry it out."`
    `<provider>` is `claudeAgent` or `codex`, for the recipient chosen in
    [delegation](../SKILL.md#choose-the-task-and-recipient). `<base>` is the fetched base ref, such
    as `origin/main`; T3 creates the worktree under `~/.t3/worktrees`. `.` is the T3 project that
    contains the current directory. The output is JSON with `threadId` and `runId`; keep
    `threadId` as the recipient identity. Without `--json`, or with `--wait` when the run ends with
    exit 1 or 2, the hooks do not learn the thread, and every later `send` to it asks.
    Before Start, check that `<branch>` exists neither locally nor in another worktree
    (`git branch --list <branch>` and `git worktree list`, each as its own call); otherwise T3
    fails the run with `branch_already_exists`. Choose another branch name, or use the existing
    worktree as [Branches and worktrees](../../development-cycle/references/branches.md) says.
- **Start** a plan review the same way, without `--worktree` and `--branch`:
    `t3 thread start --provider <provider> --model <slug> --title <review-name> --json . "Read your brief at <scratchpad>/briefs/<review-name>.md and carry it out."`
    The thread runs in the project checkout and creates no worktree or branch. The brief assigns
    a review only, so the reviewer reads and does not edit; that checkout keeps its single writer.
- **Wait** by polling **Read**, never by `send`: every `send` adds a turn to the lane. After Start,
    repeat this until the turn has ended, and use the same procedure to wait again after any stop:
    1. Run `t3 thread show --json --messages 5 <thread>` as its own call. It prints
        `{"thread": {...}, "messages": [{"role", "runId", "text"}]}`, where `thread` carries
        `status`, `activeRunId`, `latestRunId`, and `pendingRequestCount`
        (`OrchestratorMcpThreadDetail` in `packages/contracts/src/orchestratorMcp.ts`; the command is
        `threadShowCommand` in `apps/server/src/cli/thread.ts`).
    2. Decide from the state in `thread`, in this order:
        - After a Prompt, while `latestRunId` equals the one recorded before the `send`: the new run
            has not started, and the state is the previous run's. Decide nothing from it, not even
            a terminal `status` such as `failed` or `cancelled`, and keep polling. If `latestRunId`
            is still the recorded one after the third poll, stop and report to the user that the
            new run did not start, instead of polling forever.
        - `status` is `failed`, `cancelled`, `interrupted`, or `rolled_back`: the run failed or
            stopped. The CLI does not print the cause: before reporting, find it in
            `~/.t3/userdata/logs/server.trace.ndjson` by searching for the thread or run id, such
            as `branch_already_exists` when Start used an existing branch. Report the cause to the
            user; do not restart it unasked.
        - `pendingRequestCount` is above `0`, whatever `status` is (it stays `running`, because a
            pending request does not change it): the recipient waits for an answer to an approval
            or a question. The user answers it in the T3 view; the parent never answers it, through
            `send` or otherwise. Tell the user which lane waits, and keep polling.
        - `activeRunId` is `null` and `status` is `idle` or `completed`: the turn ended. The reply
            is the last message in the output whose `role` is `assistant` and whose `runId` is
            `latestRunId`. If none is in the output, run Read again with a larger `--messages`
            before reporting; never report an older message as the reply.
        - Otherwise the lane still works; keep polling. This covers `preparing`, `queued`,
            `starting`, and `running`, and also `waiting`: the turn has ended but completion is
            held by background work that counts as awaited, which is work with `awaited` true or a
            kind other than shell or monitor (`isAwaitedWork` in
            `orchestration-v2/RestartBackgroundNote.ts`; `threadStatus` in
            `OrchestratorMcpService.ts` returns `waiting` while it holds completion). Unawaited
            shell or monitor work does not hold it, so `pendingBackgroundTasks` is no part of the
            rule. `waiting` is not the approval state. Never send the brief again.
    3. While the lane still works or waits for an answer, wait between checks with a background
        `sleep 300` call, which contains no `t3`, and return to step 1 when it exits. Do not put
        `t3` inside a loop, a script, or the Monitor tool: such a call is more than one `t3 thread`
        command, so it stays in the sandbox and fails.
- **Prompt**, such as continuing a lane after `LANE-BLOCKED`:
    1. Before sending, run `t3 thread show --json --messages 5 <thread>` as its own call and record
        the thread's `latestRunId`. Right after the `send`, a Read can still show the previous run
        as finished, with its old reply, before the new run starts.
    2. Run `t3 thread send <thread> "<literal message>"`, in the foreground and without `--wait`;
        the message becomes the lane's next turn, and `send` prints no run id. If it exits
        non-zero, report that to the user and do not Wait.
    3. Wait as above. Until `latestRunId` differs from the recorded one, decide nothing from the
        state, and report that the new run did not start if it is unchanged after three polls.
- **Read**: `t3 thread show --messages <n> <thread>` prints the state, the branch and worktree,
    `Waiting for <n> answer(s).` while an answer is pending, and the latest `<n>` messages in
    full, the newest of which may not be the assistant's; add `--json` for the fields above.
- **Close**: the CLI cannot stop or archive a thread. Leave the thread in place; the user archives
    it in the T3 view.
- **Clean up**: after the user merges, run `cleanup_worktrees.py` by its absolute path with the
    home directory expanded, as shown in the rendered `excludedCommands` entry; `--dry-run` previews.
    Once the script covers `~/.t3/worktrees`, as [Prerequisites](#prerequisites) checks, it removes
    a lane worktree there on the same conditions as a Herdr one: a merged pull request's head is
    the branch tip and the tree is clean. Do not remove T3 worktrees by hand.
